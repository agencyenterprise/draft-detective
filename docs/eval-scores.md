## Results

Each eval defines its own scorers. The **Scorer results** column lists every
scorer that eval runs, by its Inspect name, with the per-scorer accuracy — see
the footnotes for what each scorer checks. Expand a cell to read them; the
summary line gives the count and the spread on each side of the deterministic
/ model-graded split, which is what **Overall avg** flattens. That average is
computed over every metric in the cell, not only the ones a reader expands. **Overall avg** is the unweighted
mean of that eval's per-scorer accuracies (a rough headline number: scorers
measure different things, so it is not a rigorous aggregate). Model-graded
scores use `openai/gpt-5.4` as the grader, except the two review-assistant
suites (17 and 18), which pin `openai/gpt-5.6-terra`.

[^abbr-rework]: `abbreviation_checker` · the agent paginates `/main.md` in 200-line chunks and records occurrences through a `record_abbreviations` tool, and each compliance rule reports once per abbreviation rather than once per occurrence (no `severity=none` informational entries). The eval's 26 samples are all short documents, so they do not exercise long-document behaviour; on a 111-page fixture the check records 975 occurrences and reports 40 issues.
[^abbr-list]: `abbreviation_checker` · deterministic match of the extracted abbreviations list against the target (inline definition, line span, section definition, ignored flag).
[^abbr-sect]: `abbreviation_checker` · deterministic check that the "Abbreviations section found" boolean matches the target.
[^ger-preface]: `about_this_ger` · deterministic match of the flagged preface / "About This" issue titles against the target.
[^ger-authors]: `about_this_ger` · deterministic match of the flagged author-biography issue titles against the target.
[^advv2-titles]: `advocacy_tone_v2` · deterministic match of the count of flagged issue titles against the target.
[^cr-align]: `claim_reference_validation_v2` · checks each citation's support label aligns with the target (supported / partially / unsupported / unverifiable).
[^cr-count]: `claim_reference_validation_v2` · checks the number of citations found matches the target.
[^issue-titles]: `document_structure` and `figures_tables_check` · deterministic match of the detected issue titles against the target.
[^tool-called]: `figures_tables_check`, `recommendation_check` and `results_extraction` · behavioural check: whether the run's transcript shows the agent calling `view_image` on a sample whose document embeds a figure. It is a plain rate over the figure samples (the metric is `applicable_mean`, so it carries no ±stderr and text-only samples are left out rather than counted as passes), and it sits next to the outcome scorers because a sample built so the right answer is only reachable from the image can still be passed by a lucky guess. `inference_validation_v2` and `reviewer_2` cannot carry it: the former delegates the reading to sub-agents whose transcripts are not persisted, the latter's state holds the two documents and no transcript. Their figure samples are built so the outcome scorers only pass if the chart was read.
[^fig-images]: Figure samples across five suites (3 in `figures_tables_check`, 2 each in `inference_validation_v2` and `recommendation_check`, 1 each in `results_extraction` and `reviewer_2`). Each document embeds a PNG chart, drawn deterministically by `evals_inspectai/files/figures/generate_fixtures.py` and inlined as a data URI at upload, that carries information the text does not: a logo that is not a figure, a caption rendered inside the image, an author's placeholder box where a chart should be, tercile means that exist only in a bar chart, a pair of documents with identical text whose charts make the same claim true or false, and a sub-point effect drawn on a truncated axis. The inference pair states its false premise and false conclusion in one sentence, since the skill counts one candidate per sentence.
[^inf-count]: `inference_validation_v2` · deterministic match of the count of reported invalid inferences against the target. An informational (`none`) issue fails the sample outright rather than counting towards the total: this assessment reports invalid inferences only, so sound reasoning is reported as nothing at all.
[^score-structure]: `literature_review_v2` and `live_reports_v2` · structural checks averaged into a `[0,1]` score (result present with non-empty report, issue count within the expected band, sane line ranges, citation-like detail when recommendations are expected). Exact sources aren't asserted because web search is non-deterministic.
[^meth-structure]: `methodological_alignment` · structural checks averaged into a `[0,1]` score: a non-empty report carrying the skill's five sections (extracted methodology, field overview, alignment, rigor and risks, suggestions), at least one web citation as a markdown link, at least the sample's minimum number of issues, sane line ranges on every issue, and no informational (`none`) issues. The comparison prose is free-form and the field baseline comes from live web search, so exact wording and sources aren't asserted.
[^rec-rewrite]: `recommendation_check` · on the issue-inventory structure (`evals_inspectai/common/issue_inventory.py`): ground truth is one expected issue per recommendation occurrence, anchored by its wording, with the severity its classification maps to (`none` supported, `medium` partially supported, `high` unsupported). `severity_correct` misses are one-step classification disagreements on the same few borderline items (the near-miss reporting, permanent-briefings, flat-chart and summary e-book budget recommendations), a different one or two per run; read anything between 0.93 and 1.0 on `severity_correct` and `precision` as the workflow's variance on those items. The rationale behind a verdict is not scored.
[^rec-inventory]: `recommendation_check` · seven deterministic detection checks against the inventory: `recall` over the required expected issues, `precision` over reported issues (one reported issue may cover at most one expected issue, so a run that merges a restatement with its original, or folds an actionability finding into a support issue, loses recall on the second), `f0_5`, `clean_document_untouched` on the document with no recommendations, `title_correct` for the three fixed-title kinds, `severity_correct` as the classification check, and `anchor_in_range` for the line bracketing the recommendation. Support issues have free-form titles and are matched on the recommendation they quote or bracket; an issue under one of the fixed titles is paired with a support expectation only when no free-form report of that recommendation exists, so an extra actionability or audience issue on the same line costs precision and cannot stand in for the support verdict.
[^rec-decoys]: `recommendation_check` · one metric per exclusion the skill states. Conclusion sentences that restate findings must not be read as recommendations at all. Every other decoy is a recommendation a correct run reports for support but must not report under one kind, so it carries that kind's title: no unclear audience where a lead-in or a heading names who acts or where the document is about one organization's or programme's own work; no not-actionable issue on a concrete action, a concrete action left without a number, or a hedged but concrete one (*consider extending*); and no length issue on a list of three or fewer, on a summary and detailed list that restate the same three, or on sub-points that elaborate one recommendation.
[^rec-eei]: `recommendation_check` · also checks that recommendations are actionable, concise, well-specified and targeted, and that more than three are pared down. Alongside the support classification, the skill reports three issue kinds with fixed titles: `Recommendation Not Actionable` (medium) and `Recommendation Audience Unclear` (medium), once per recommendation on its most detailed statement, and `Too Many Recommendations` (low), once per document. No edits are proposed: which action and which actor the authors mean is theirs to decide. The 15 records include two optional expectations (the near-miss recommendation's "continue to encourage" and the contractor rollout's audience, both defensible either way) and cover a multi-actor workforce report, a broadband report with goal-as-action and "stakeholders" recommendations, a five-recommendation hospital list, a lead-in audience with sub-points, a heading audience with hedged and unquantified actions, a well-formed two-recommendation report, and a single-actor pharmacy review. **Read the three fixed-title kinds' numbers as a dev-split figure**: seven of the records were written and labelled against this workflow. The current `severity_correct` misses are the near-miss recommendation called partially supported in all three epochs, permanent briefings called supported once, and the coastal pilot's more-sessions recommendation called partially supported once. On three real documents the check reports 18, 7 and 89 issues: a five-recommendation EU AGI-preparedness list flagged as too many with a keep-and-merge plan and one "rigorous, anticipatory" quality-not-action; a five-recommendation USAF readiness draft flagged as too many with one unclear audience; and a 62-recommendation biodefense report with one length issue, six not-actionable ("invest in developing novel platforms", "explore additional sample sources") and seven unclear-audience issues, mostly on "future work should" research calls.
[^rec-judged]: `recommendation_check` · three criteria graded by `openai/gpt-5.4` on Inspect's model-grading protocol, one call per detected issue of each fixed-title kind, against the recommendation it is anchored to: a not-actionable issue's suggested action proposes a concrete, checkable step or asks what action is meant; an unclear-audience issue's asks the author to name who should act, candidates allowed, without settling on a guess; a length issue's names which recommendations to keep and which to merge, cut or move. Not yet calibrated against labelled pairs.
[^refdl-conclusion]: `reference_downloader` · deterministic match of the final download conclusion against the target.
[^refext-refs]: `reference_text_extractor` · deterministic match of the extracted bibliographic references against the target.
[^refval-result]: `reference_validation_v2` · deterministic match of the final validation result label against the target.
[^res-devsplit]: `results_extraction` · **read this as a dev-split figure, not an unbiased estimate.** Ten of the eleven samples were built and tuned against this workflow, and eight of those ten documents are synthetic. `tests/unit/evals/test_reproducibility_dataset_arithmetic.py` and `evals_inspectai/e2e/results_extraction/verify_reservoir_yields.py` re-derive the numbers behind every fully-reproducible expectation. `class_accuracy` varies between about 0.88 and 0.99 across runs of an unchanged configuration; on ten samples a five-point swing between runs is ordinary, and a regression has to clear that before it means anything. Held-out samples are the outstanding work: blind-authored documents, one adversarial case that falsely claims reproducibility, and one full-length real report. Until those exist, treat this eval as a tripwire for large regressions rather than a quality score.
[^res-shape]: `results_extraction` · seven deterministic checks on the shape of the delivery: a substantive markdown report, an inventory table in it (found by the reproducibility column its header names, not by being the widest table in the report) with at least a row per reported result, at least as many results as the dataset declares, a recognised reproducibility label in every issue title, the severity split the skill mandates (anything reproducible is informational `none`; only not-reproducible carries a real severity), line ranges that land inside the document, and no result reported twice. None of these say whether a classification is *right*.
[^res-truth]: `results_extraction` · four deterministic checks against the dataset's own ground-truth inventory, which names every result each document presents together with the class it should be given and how much the document rests on it: whether every expected result was found, the fraction given the right reproducibility class, whether anything was reported that the document does not present as a result, and whether the severities of the non-reproducible results are ordered by importance. Which of low/medium/high a result earns is the agent's judgement, so only the ordering is asserted, not the level.
[^res-rubric]: `results_extraction` · two judged criteria, each graded three times with the median taken, because single grader calls disagreed with themselves across repeats of an unchanged output. `classification_grounded` asks only whether each rationale names the ingredients present or missing and how a reader would obtain them; it is given the four class definitions and the list of absences the skill says are *not* deficiencies, since without them the grader marked down rationales for correctly declining to treat an unrendered figure or a fixed-seed simulation as a gap. `sample_expectations` is the dataset's own per-sample rubric. Both use a requirement-shaped prompt rather than Inspect's model-graded-fact template, which asks whether the submission *contains* the expert answer and misgrades a criterion that states a property the output must have.
[^ra-structure]: `reviewer_coverage_report` and `revision_planning_summary` · the rules the `review-assistant` skill states outright, checked deterministically against the report's HTML: every reviewer memo reproduced verbatim, that reproduced text sitting inside a marked quote, a valid per-reviewer point-ID scheme numbered from 1 with no gaps, a self-contained document (no external stylesheets, fonts, scripts or images, and no `<script>`), a visible two-part split with a short first part, and none of the generic-assistant tells the `voice-and-tone` skill bans, counted only outside quotes so the reviewer's own punctuation is not held against it.
[^rcr-bookkeeping]: `reviewer_coverage_report` · the arithmetic of the summary table, checked deterministically: all four verdict categories present including the ones that scored zero, every point accounted for exactly once and at one granularity with the stated counts matching the IDs listed, the four-point scale actually used in Part 2 rather than only declared in the table header, and Part 1 stating the sign-off decision outright. Whether an individual verdict is *right* is judged separately.
[^rcr-rubric]: `reviewer_coverage_report` · four judged criteria, each graded in its own call so one weak area cannot colour the rest: each point's verdict is correct against both drafts, Part 1 is decision-grade for a QAM, each verdict cites evidence and a location, and a per-scenario trap criterion for the specific failure that scenario is built to provoke.
[^rps-rubric]: `revision_planning_summary` · four judged criteria, graded one call each: reviewer points located by content rather than by numbers the revision will move, Part 1 triaging substantial asks apart from quick fixes, a planning note under each quoted point carrying scope and location and a suggestion, and a per-scenario trap criterion.
[^av-devsplit]: `active_voice` · a skill-declared workflow (`skills/active-voice/SKILL.md`, see [`docs/skill-workflows.md`](./skill-workflows.md)) on the issue-inventory structure: ground truth is a list of expected issues, each anchored by a verbatim quote and carrying edit expectations, plus decoy sentences that must not be flagged, scored by the reusable `issue_checks` and `decoy_checks` scorers in `evals_inspectai/common/`. **Read this as a dev-split figure.** The 20 records (9 one-rule snippets, 8 clean documents, 3 section-length documents) were labelled against this workflow, and the skill was tuned on three real reports; nothing here has been measured on samples the workflow never influenced. Known gaps: a comma stranded after a moved footnote marker in every epoch, which is what `edit_punctuation` and part of `edit_expected_phrases` record; a stative "are located in the Midwest" flagged in every epoch; generic modal passives such as "might be coordinated through private channels" flagged in two epochs of three; and the transit document's ambiguous-actor sentence missed or given a guessed actor. A guessed edit rewrites the whole sentence, so it also touches the sentence's active second clause ("the transit authority will decide"), which is what `no_fp_active` records. A passive whose actor the document never names (the CERN draft's research focus) is occasionally given an actor rather than a question.
[^av-detection]: `active_voice` · seven deterministic detection checks against the inventory: `recall` over required expected issues, `precision` over reported issues (a report counts as correct when it covers at least one expected issue), `f0_5` weighting precision twice as much as recall as in grammatical-error detection, `clean_document_untouched` on the eight documents with nothing to report, and, of the covered issues, the share with the expected title, severity and a line range that brackets the anchor.
[^av-edits]: `active_voice` · six deterministic edit-hygiene checks over the proposed edits of covered issues: an edit attached where one is expected and none where none is, the replaced text quoted verbatim from its line, the replacement carrying the phrases the inventory expects (and none it forbids), every number, footnote marker and citation kept, and no stranded punctuation introduced. `edit_expected_phrases` is the strictest label in the set: a rewrite that names a defensible actor by other words than the inventory's fails it.
[^av-decoys]: `active_voice` · one metric per exclusion rule the skill states, `no_fp_<reason>`: the share of that reason's decoy sentences left unflagged. Reasons name the rule that would misfire (stative participle, generic actor, idiom, participial modifier, source qualifier, quoted wording, excluded material, a sentence whose point is the actor, an already-active sentence). A NaN would mean the run gave a reason nothing to judge; every reason has samples here.
[^av-passive]: `active_voice` · the workflow's own deterministic check: the replacement has fewer be-plus-participle constructions than the original, by a regex heuristic that knows irregular participles and intervening adverbs. An edit whose original shows the heuristic no passive is left unscored rather than passed.
[^av-judged]: `active_voice` · three criteria graded by `openai/gpt-5.4` on Inspect's model-grading protocol, one call per edit or issue: the rewrite preserves meaning while naming only the actor the text supports, it reads at least as well in place, and, for passive issues whose actor the document never names, the suggested action asks the author rather than guessing (a detected issue with no suggested action scores 0). The two edit criteria were calibrated against 14 human-labelled edit pairs (`active_voice_judge_calibration`) before being trusted.
[^cp-devsplit]: `concision_precision` · a skill-declared workflow (`skills/concision-precision/SKILL.md`), checking concision (no run-ons, filler or wordy constructions, including a list of stock wordy phrases) and precision (no vague references, empty framing or statements of the obvious), on the issue-inventory eval. **Read this as a dev-split figure.** The 15 records (8 one-rule snippets, 5 clean documents, 2 documents including a section-length fixture) were written and labelled against this workflow, and the skill was tuned on three real documents (a 12,000-word essay, a 50,000-word draft report and the demo report); nothing here has been measured on samples the workflow never influenced. Two workflow behaviours set the current score. First, in one epoch of the section-length fixture (sample 15) the agent quoted whole paragraphs, up to 473 characters, as each edit's original text rather than the sentence it changes; the issues skill permits widening a quote up to the whole line, and in this fixture a paragraph is one line. Every decoy inside those paragraphs then counts as touched, which is what `no_fp_clear_referent` (0.667), `no_fp_compound`, `no_fp_hedge`, `no_fp_qualifier` and `no_fp_signposting` record; the other two epochs quoted sentences. This is a precision risk in the Word export (a whole-paragraph redline where one sentence changes) and is worth a skill line limiting an edit's original text to the sentence it rewrites. Second, the ambiguous "This makes implementation difficult" (sample 7), whose referent could be the funding timing or the stipend cap, is given an edit naming the timing gap in two epochs of three instead of an action asking the author; `edit_absent_when_not_expected` has only that one expectation, so it reads 0.333. On the three real documents the check reports 1, 12 and 23 issues (demo report, essay, draft report); its two run-on findings on the draft report are comma splices, and it does not review appendices.
[^cp-inventory]: `concision_precision` · the shared detection and edit-hygiene checks (see [^av-detection] and [^av-edits]): six issue titles, one issue per paragraph for wordy constructions and one per sentence otherwise, each anchored to the sentence and, where the fix is fully determined, carrying a proposed edit. A deletion is an edit with an empty replacement.
[^cp-decoys]: `concision_precision` · one metric per exclusion the skill states, `no_fp_<reason>`: signposting sentences, source qualifiers, hedges, compound sentences joined by a comma and a conjunction, topic sentences that announce specifics, first person, technical terms, precise long sentences, two clear sentences, quoted wording, a named referent that only looks vague, and a sentence stating a framework's aims.
[^cp-passive]: `concision_precision` · the workflow's own deterministic check: the replacement introduces no be-plus-participle construction the original lacked (the same heuristic Active Voice uses to see a passive); deletions are not scored.
[^cp-judged]: `concision_precision` · two criteria graded by `openai/gpt-5.4` on Inspect's model-grading protocol, one call per edit: the tighter rewrite keeps every claim, qualifier, number and citation (a deletion is correct when the flagged sentence carried none of those), and it reads at least as well in place (a deletion is correct when the paragraph reads naturally without it). Not yet calibrated against labelled pairs; the Active Voice criteria they were adapted from were.
[^wc-devsplit]: `writing_consistency` · a skill-declared workflow (`skills/writing-consistency/SKILL.md`), checking consistent terms and tone across chapters, one verb tense for findings, and the house-style compound `decisionmaking`, extended to spelling, hyphenation and number style. A whole-document judgment: one issue per inconsistency, anchored at the first minority occurrence and listing every variant. **Read this as a dev-split figure**, on the same terms as [^cp-devsplit]: 15 records (9 planted inconsistencies in two-chapter snippets, 5 clean documents, 1 section-length fixture with six), labelled against this workflow. The misses are students/pupils missed once in three epochs on the section-length fixture, and one edit on the before-noun hyphenation snippet (sample 6) that changes more than three words, failing `edit_minimal_change`. On three real documents the check reports 2, 8 and 9 inconsistencies, each with occurrence counts and the lines of the minority form; the 50,000-word draft's nine include data center/datacenter (188 to 25), co-located/collocated (11 to 9) and decision-making/decision making against the house style.
[^wc-inventory]: `writing_consistency` · the shared detection and edit-hygiene checks. Titles carry the variants after a colon (`Inconsistent Term: students / pupils`), so the inventory names the stable prefix, matched as whole words within the reported title; a pair that could fairly be called spelling or number style is labelled with the bare prefix `Inconsistent`. Phrases expected of an edit are read off the line with all of the issue's edits applied, since these edits swap single words.
[^wc-decoys]: `writing_consistency` · one metric per legitimate variation the skill must leave alone: different names for different things, a term glossed then shortened, a compound open after a verb and hyphenated before a noun, singular against plural, quoted wording and titles, tables and figures with their own number conventions, present tense for general truths, signposting and interpretation, and proper names.
[^wc-minimal]: `writing_consistency` · the workflow's own deterministic check: an edit changes at most three words of the original, the variant and its immediate neighbours; a run that rewrites a whole span to fix one variant fails it.
[^wc-judged]: `writing_consistency` · one criterion graded by `openai/gpt-5.4`, one call per edit: only the variant changed, to the form the document settles on, with the sentence's meaning intact. The grader is told to treat the replacement's form as the chosen one, since it does not see the document, and that `decisionmaking` is a deliberate style rather than a misspelling. Not yet calibrated against labelled pairs.
[^hs-devsplit]: `headers_skimmability` · a skill-declared workflow (`skills/headers-skimmability/SKILL.md`), checking skimmability (bottom line up front, headers that telegraph the section's point and match its content, bold lead sentences that argue, header suggestions of 2 to 8 words that keep section numbers and never outrun the findings) and a key findings box of about six brief items. It proposes no edits: header feedback is a comment suggesting new wording, never a rewrite, so the suggestion sits in the suggested action as `Suggested header: "..."`. *Summary*, *Introduction*, *Conclusion* and *Recommendations* headers are exempt as the names readers look for, like *Key Findings*, and headers naming the concepts an essay assesses are protected like *Option* headers. **Read this as a dev-split figure**, on the same terms as [^cp-devsplit]: 16 records (7 one-rule snippets, 7 clean documents, 2 section-length fixtures with six and eight expected issues) written and labelled against this workflow. What remains is mostly judged: the model borrows the introduction's causal wording ("Tutoring Raised Reading Scores"), which the grader, seeing only the section, reads as a causal claim from a comparison; and chapter headers on the section-length fixtures compress a mixed finding into 2 to 8 words ("Losses Fell, but Customer Services Lagged") and get half credit on `suggestion_supported`. One suggested header ran to nine words. On three real documents the check reports 3, 2 and 5 issues (demo report, 12,000-word essay, 50,000-word draft report); the draft's five are all in its findings chapters, after three chapters of background and framework it correctly leaves alone.
[^hs-inventory]: `headers_skimmability` · the shared detection checks (see [^av-detection]) with no edit keys: seven issue titles, one issue per header, lead sentence, key finding or key findings box and one per document for a missing bottom line, paired one to one. Header anchors are the header text, with an explicit line where the text recurs in the prose.
[^hs-decoys]: `headers_skimmability` · one metric per exclusion the skill states: procedural headers (methods, data, background, limitations, appendices), protected headers (*Option*, the publishing division's header), headers naming the alternatives an assessment compares, headers readers look for by name (*Summary*, *Introduction*, *Recommendations*), the document title, signposting sentences, bold labels on methods content, bold emphasis inside a sentence, and bold openers that already state their point.
[^hs-suggestions]: `headers_skimmability` · the workflow's own deterministic checks on the suggested wording, read from the suggested action: the action begins with it in the skill's `Suggested header: "..."` / `Suggested lead: "..."` form, a suggested header runs 2 to 8 words not counting its number, and a numbered header keeps its number exactly as written, delimiter and capitals included. Markdown marks around the wording are ignored.
[^hs-judged]: `headers_skimmability` · two criteria graded by `openai/gpt-5.4`, one call per header or lead-sentence issue, each shown the whole section the header opens (the judge's `passage="section"` option) rather than the header alone: the suggested wording asserts nothing the section does not show (no causal claim from a comparison, no dropped qualifier or subgroup), and it states the section's main point rather than its topic. Both tell the grader a header of 2 to 8 words compresses and cannot carry every point. Not yet calibrated against labelled pairs.
[^ns-devsplit]: `narrative_synthesis` · a skill-declared workflow (`skills/narrative-synthesis/SKILL.md`), checking that chapters and information are in logical order, that data is synthesized rather than dumped, that the main body runs 30 pages or fewer, that the document answers three framing questions (why it matters, what is new, what happens next), and that points are not restated across sections. Header mismatches are left to the Headers & Skimmability check, so the Editorial Review preset does not flag one header twice. A whole-document check that proposes no edits: one issue per data dump or restated passage, one per unanswered framing question, one for order and one for length. **Read this as a dev-split figure**, on the same terms as [^cp-devsplit]: 15 records (4 one-chapter excerpts, 10 short whole reports, 1 section-length report with three planted findings; 5 clean), labelled against this workflow. The one detection miss is one of the apprenticeship report's two data dumps (the enrollee counts or the year-by-year earnings) in one epoch of three. **Length is not in the inventory**: the agent has no word counter, so it estimates, and the threshold (about 15,000 words) needs a long document to test. On the two published reports in `evals_inspectai/files/` it estimated 26,000 and 25,000 words for main bodies of 28,680 (RRA4636) and 24,685 (RRA4036) and reported only the first, treating the biodefense modeling report as technical. Those runs also returned no data dumps or restated points on either report, and one defensible "What Is New" on RRA4636, whose introduction states its scope but not the gap it fills. A deterministic word count would be more reliable than the estimate; the skill-declared path has no code step to hold one. **Nor is the volume cap**: no record has more than five data dumps or restated points, so the `Data Without Synthesis: Recurring` roll-up is untested. `takeaway_within_evidence` is kept to the per-passage title on purpose: a roll-up's action spans passages the grader is not shown, so grading it against one passage would mark supported takeaways as unsupported.
[^ns-inventory]: `narrative_synthesis` · the shared detection checks (see [^av-detection]) with no edit keys, paired one to one: six titles, and a report missing two framing questions has both anchored on the same introductory paragraph, so each must be reported separately. Order, why it matters and what is new are anchored to the introductory section and what happens next to the concluding (or last) section, which is where the skill anchors them.
[^ns-decoys]: `narrative_synthesis` · one metric per exclusion the skill states: data interpreted in the same paragraph or at the start of the next, a single comparison, a single statistic in a sentence that makes its point, a table and the sentence that points to it, methods numbers, appendix data, summaries and chapter summaries that restate by design, a one-clause reference back, signposting, framing answered in a summary instead of an introduction, and a mismatched or vague header, which belongs to the header check.
[^ns-rule]: `narrative_synthesis` · the workflow's own deterministic check over every reported issue: its text does not cite editing rules, guidelines or a style guide, since feedback should explain the problem rather than point to a rule, by a regex that lets "the rule change in 2023" through.
[^ns-judged]: `narrative_synthesis` · two criteria graded by `openai/gpt-5.4`, one call per detected issue on its suggested action, each shown the anchor's passage (`passage="section"`: the paragraph, wrapped lines included, or the whole section for a heading anchor): the action is specific to the passage rather than advice that fits any report, and, for data dumps, any takeaway it proposes stays within the passage's figures. The remaining partial grades are order and framing actions the grader reads as generic, since it sees the introductory paragraph and not the sections being moved. Not yet calibrated against labelled pairs.
[^af-devsplit]: `audience_fit` · a skill-declared workflow (`skills/audience-fit/SKILL.md`), checking for a specific target audience, named once, with no contradiction between the preface and the introduction, and for vocabulary that suits the audience (technical terms, notation and methods detail in plain language or an appendix for policy and practitioner readers, left alone for technical ones and in appendices). The check decides the audience once, from what the document states or, failing that, from who could act on its findings, and judges every main-body paragraph against it. It proposes no edits: naming the audience is the author's call, and putting a technical idea in plain words is a rewrite whose meaning the author has to check. **Read this as a dev-split figure**, on the same terms as [^cp-devsplit]: 16 records (8 one-rule snippets, 6 clean documents, a section-length fixture with three issues, and one with 17 technical paragraphs for the issue cap), written and labelled against this workflow. The technical-audience sample carries an appendix, so a run that sends its main-body methods there shows as a false positive. At 1.000 on every metric in every epoch, the set does not discriminate; it is a tripwire for regressions, and harder samples (a mixed policy-and-research audience, borderline field terms, a long methods chapter) are the outstanding work. On four real documents the check reports 6, 6, 4 and 1 issues. Energy Considerations for Data Center Siting: its framework chapter as one appendix-move passage (opening with multicriteria decision making) and power-system terms such as ELCC and capacity accreditation. The demo report: a missing audience plus research-design labels (narrative review, observational, pooling). The CERN for AI draft: audience missing, two economics terms, and the five-forces derivation as a passage. The USAF readiness assessment: audience missing, with its defense vocabulary set aside as the audience's own.
[^af-inventory]: `audience_fit` · the shared detection checks (see [^av-detection]), with one reported issue covering at most one expected issue (`one_to_one`), since each audience problem is reported once per document and each technical paragraph or passage once. No edits are proposed, so the edit-hygiene keys are not emitted.

[^af-judged]: `audience_fit` · five criteria graded by `openai/gpt-5.4`, one call per detected issue, on its suggested action (the fifth, `overflow_summary_alternatives`, is described under [^af-overflow]). Each grader also sees the source the action must agree with: the anchor's paragraph for a paragraph of technical language (`passage="section"`), so a changed or dropped finding shows, and the whole report (`passage="document"`) for a technical passage, which runs over paragraphs the anchor's does not show, and for the audience issues, so an audience the report does not point to, or a conflicting one it never states, shows.
